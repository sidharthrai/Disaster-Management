# Organization approval implementation

Applications are stored in the `organizationApplications` SQLite collection, with a default empty list for older state. The applicant submits a description, ordinary service categories, and general areas. The server records the applicant, community, submission time, status, and decision history. Coordinators can approve or decline pending applications and revoke an active approval created by this workflow. Applicants can withdraw pending applications. All decisions require the same community and coordinators cannot decide their own application.

Approval makes an eligible member or unverified organization an ordinary verified organization. Sensitive service claims are rejected. An account with an existing medical or missing-person qualification cannot be approved through this workflow, because verification would activate the dormant qualification; an operator must review it. Revocation clears verification while preserving the role, qualifications, resources, commitments, and history. Existing matching excludes unverified owners. Existing resource editing and availability operations still allow an unverified owner to edit retained resources; new resource creation is blocked.

The private API uses `GET /api/organization-approvals` and `POST /api/organization-approvals`. GET returns `{ applications }`, scoped to the actor's own applications or their coordinator community. POST accepts strict action objects for `apply` with `input`, `withdraw` with `id`, and `approve`, `decline`, or `revoke` with `id` and a nonempty `reason`. It returns `{ ok: true }`. Identity and privileges are derived on the server.
