# Feature status

Updated November 11, 2026. This inventory describes the current local implementation. The [original handoff coverage audit](original-handoff-coverage.md) is a historical baseline, so its findings describe the earlier state; see the [completion update](completion-update.md) for subsequent work and verification.

| Area | Current local behavior | Limits |
| --- | --- | --- |
| Intake and safety | Request intake offers editable classifications, reviewed urgency and timing, source and private provenance, and supported people-count and mobility details. Provider-derived safety flags carry through creation. Members can privately save incomplete drafts and resume the analyzed, signed-preview and reviewed-time request flow when ready. | Drafts are not published or matched; only the author and same-community coordinators can access them. Pasted channel examples do not ingest real calls, messages or social posts. |
| Matching and case lifecycle | Eligible offers and resources produce explainable suggestions. Requester and helper agreement, private coordination, per-need delivery confirmation and documented non-success closures persist locally. | A suggestion is not a dispatch or a guarantee of capacity or help. |
| Coordinator operations | Overview counts and helper filters distinguish proposed connections from case ownership. Queues support corrections, private notes, review, moderation and closure, with a visible case reference. | Human review is still required; the system does not autonomously respond to emergencies. |
| Follow-up and notifications | Persistent condition episodes support configurable thresholds, acknowledgement, escalation and resolution. A single-process timer checks conditions every 1–60 minutes (default 1) and can create private recipient-scoped in-app reminders. | The timer runs only while the persistent Node server is running and is not a hosted scheduler. Account mode uses server time; demo mode uses simulated time. No external delivery, automatic outcome confirmation, assignment or closure occurs. |
| Emergency and resources | Incident banners direct each role to its own readiness actions, and the member board prioritizes urgent incident requests. Coordinator review queues cover available and unavailable shelter and transport. Incident linked requests, resource reconfirmation, unresolved needs, helper context and resource request actions support the end-to-end flood scenario. | Readiness and resource availability are simulated; coordinators still review and participants retain consent. There is no actual dispatch, professional credential verification or medical or missing-person operation. |
| Organization profiles | Same-community directory entries combine authoritative identity and verification with organization-editable description, service areas, categories and HTTPS website. Member organization applications and coordinator review, approval, decline, withdrawal and revocation are available in account mode and the synthetic demo. | Organizations cannot grant themselves verification or qualifications; missing-person advertising is rejected. Approval does not establish external identity or medical or missing-person qualifications. |
| Community activity | A signed-in feed projects safe posted and confirmed activity, excluding restricted and other-community requests and free text. Neighborhood gatherings support bounded capacity, joining, leaving and organizer/coordinator cancellation. Seeded cases include coherent transition history. | Participant names and private organizer notes are restricted to the organizer and same-community coordinators; general listings show counts and the current member's attendance. |
| Coordinator insights | Coordinators can view community aggregate counts, participation, first-acceptance timing samples and per-resource availability. | Aggregates are local data, not verified impact reporting; timing excludes invalid histories and resource units are not interchangeable. |
| Group activities | Neighborhood gatherings have bounded capacity, dated windows and create/join/leave/cancel actions. General listings show counts and personal attendance; organizer/coordinator details can show opted-in participants. | These are community activities, not emergency response. Cancellation retains attendance history. |
| Weekly offer windows | A confirmed schedule creates independent offers for one to four Chicago-local weekly windows across selected neighborhoods, with UTC previews. Offers can include an optional self-described organization affiliation. | This is a bounded batch, not an ongoing scheduler; specialized categories cannot be scheduled. Affiliation is not verified or endorsed and does not affect matching or permissions. |
| Volunteer profiles | Members can opt in to a community directory with ordinary capabilities, general areas and languages; names come from the current account and eligible offer counts are shown. Members can hide their profile at any time. | No contact information, precise location, specialized qualifications or automatic enrollment is included. Existing matching and mutual consent govern connections. |
| Donations and neighborhoods | The donation board shows eligible groceries and supplies without owner or description text. An interactive Leaflet/OpenStreetMap base map shows five fictional neighborhood markers over Chicago; marker selection and zoom were verified. | Units are per resource and not a stock guarantee. Marker positions are illustrative only, not incident coordinates, GPS, routes, shelters or live hazards. Tiles require network access to OpenStreetMap. |
| Language and speech input | The interface supports English and Spanish dictionaries, with English-first rendering and a saved local language choice. Literal translation keys are covered in fixed interface components. Browser speech input appends recognized text to the editable intake field; users can start, stop or cancel. | No human translation audit or automatic user/model text translation is claimed. Spanish intake safety/extraction has a bounded fallback. The microphone/permission flow was not tested; typed input remains available. |
| Disaster presentation | The `/disaster` experience has a distinct amber/rust theme and presents incident-focused workflows separately from everyday help. | It remains a local simulation; the visual theme and map do not indicate real hazards or dispatch capacity. |
| Community missing-person support | Coordinators can create private people reports with optional age (unknown/adult/minor), last-seen details and context, ask questions and review author replies and status history. A deliberately broad community can receive redacted notices; members can submit their own named check-in or private tip. Adults can separately authorize use of their name, and revocation clears consent. | Fictional local coordination only: no public search or dispatch. Community notices are opt-in and redacted. Administrative closure is not reunification. Members cannot see coordinator-only report fields. The three dedicated disaster screens currently fall back to English. |
| Accounts and persistence | Better Auth registration and login map account identities to member users in a separate initially empty account database. Local password recovery writes reset links to a private filesystem outbox for operator delivery. Members can apply for ordinary organization approval; coordinators can approve, decline or revoke with a reason, and applicants can withdraw pending applications. | Remote email delivery and email verification are disabled. Recovery is limited to loopback installations and assumes trusted local filesystem operators. Organization approval does not verify identity or grant medical or missing-person qualifications; those require operator review. There is no multi-community administration. SQLite uses JSON payloads and is intended for a single instance, not normalized multi-instance storage. |
| AI providers | Deterministic fallback works without credentials; a live Ollama run with `ministral-3:3b` passed extraction validation and produced the expected fictional groceries, people-count and timing fields with a signed preview and no fallback. | The run covered one fictional message and took about six seconds; it does not establish general model quality. Hosted inference is unconfigured and untested. |

The latest run passed 169 tests across 46 files, type checking and a diff whitespace check. Eight HTTP scripts passed against isolated development servers, and the live Ollama API path was separately verified. Browser checks confirmed the map and disaster experience, including a member's safe shared check-in and community tip; broader route-by-route review remains in progress. The earlier integration baseline passed 123 tests across 30 files and a production build; no newer production build was run. Optional public search, emergency dispatch, SMS/social ingestion and payments remain outside scope. Public deployment and Docker execution remain unverified.
