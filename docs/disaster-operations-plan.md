# Disaster response workspace

The disaster area is an operational entry point for the existing community network. The earlier advocacy page made tools hard to discover and did not provide a dedicated people workflow. The response workspace makes incident context, private people reporting, urgent intake, shelter and transport availability, and active needs directly actionable.

## User journeys

- A member opens `/disaster`, sees the current incident or readiness mode, and chooses a concrete response action. The page identifies the actor’s role and labels simulated incidents explicitly.
- A member submits a private missing-person report using a name, relationship, coarse neighborhood, age group (adult, under 18, or unknown), and legitimate-reason acknowledgment. Optional last-seen time and a short private context give a coordinator something to follow up without forcing unknown details. Only its author and same-community coordinators can retrieve it. A coordinator moves the report through review states and can request more information; only the author can reply. Private history records the exchange and status changes. Closing a report is administrative and does not claim a person was found or rescued.
- A person records their own safe check-in. The server determines the author from the signed-in identity. This is self-reported, private to that person and same-community coordinators, and never automatically reconciles a missing-person report.
- The authenticated community can participate through an opt-in board. A missing-person notice normally shares only its reference, general neighborhood, and administrative status. An adult’s name can be included only through separate explicit authorization to share it with the signed-in community; the server forbids that option for under-18 or unknown ages. Age group, context, follow-up questions, and tips never enter the community projection. A member can send private information on a shared notice to its author and coordinators. A check-in author can separately opt to share their own display name, neighborhood, and self-reported safe status. Sharing defaults off and authors can revoke it.
- A person chooses urgent help and enters the existing intake flow. After analysis, the supported urgent entry preselects Urgent for ordinary requests; safety flags or an existing critical recommendation preserve Critical review. The requester still reviews the details, chooses a future time window, confirms timing, edits urgency where permitted, and explicitly creates the request.
- A person filters shelter and transport resources by service and neighborhood, reads freshness, remaining resource units, and incident readiness, then opens prefilled ordinary intake. Availability is general readiness rather than a booking or a promise of suitability. Unavailable listings explain their blockers. Resource owners can manage listings in the existing catalog.
- A member or coordinator filters the response queue to visible community needs, their own requests/connections, or the current incident. Ordering prioritizes urgency, overdue windows, and age. The queue links to the existing consent, human review, progress, and requester-confirmation workflows.
- A Riverton coordinator can start or end a simulation directly from the visible incident controls. New incident activation changes the readiness context; it does not automatically activate resources or dispatch assistance. Existing requests remain tracked after a simulation ends.

## Boundaries

People records use an additive `peopleRecords` collection and SQLite table through the existing repository and state validation. Empty defaults preserve existing databases and the regular demo reset replaces these records with the empty seed collection. The people API enforces authentication, same-origin JSON mutations, bounded bodies, and private/no-store responses. It returns separate private and narrowly constructed community projections; the board is scoped to the signed-in community rather than the unauthenticated internet. The standard network snapshot, public impact views, ordinary matching, and community request listings do not include the private records.

The people form does not request photos, precise locations, or contact details; brief context and follow-up messages are private and carry instructions to omit those details. Age group and legitimate reason come from the reporter, not independent verification. Missing children and immediate danger require contacting appropriate authorities directly; a private app report does not notify them. There is no public missing-person search, identity matching, live alert feed, emergency dispatch, rescue assignment, or medical qualification claim. Status history is private, and safe check-ins do not establish verified wellbeing.

The existing community request system remains the source of truth for ordinary support and its mutual consent and requester confirmation rules remain in force. Resource units are not automatically beds, seats, or people. Incident operation remains a labeled Riverton simulation; account identity does not establish emergency authority or professional qualification. General incident broadcasts and live external alerts remain outside this implementation.

## Implementation and verification

The hub composes independent people and support panels, uses the current safe network snapshot for the response queue, and keeps controls local to the interaction. The warm amber/rust disaster shell is preserved. Existing locale hooks remain in use; new copy uses English fallback and no additional translation project is included.

Focused verification covers people visibility and authorization, strict field validation, self-only check-ins, review history and private follow-up permissions, redacted opt-in community projections, sharing revocation, tip permissions, resource eligibility/readiness and community isolation, and urgent-entry safety precedence. Parent integration verification owns real browser journeys and the combined regression suite. No production build, default database reset, external messaging, additional dependency, or live deployment is required for this work.
